# Universal Admin Builder 2.0

## Mission
Deliver accessible, responsive, dense-but-readable, fully interactive business applications with a coherent Soft Enterprise UX. Prioritize operator outcomes and reusable metadata-driven contracts over hardcoded pages. This skill supports **frontend prototype**, **API-connected frontend**, and **full platform** modes; do not assume the request grants backend, migrations, deployment, or external-action authority.

## Non-negotiables
1. Inspect the existing repository, framework, routes, dependencies, branding, APIs, security boundaries and scripts first. Preserve working behavior and project conventions. Do not delete/migrate without explicit permission.
2. Identify delivery mode, domain, users, entities, permissions, work outcomes, actual data source and permitted operations. Infer small reversible details; ask only for consequential gaps.
3. Use the canonical resource/field/master/relationship definition for grids, forms, filters, search, inspectors, reporting and permitted actions. Do not duplicate business meaning across UI implementations.
4. Enforce tenant isolation, resource/row/field authorization, status transitions and sensitive-data policies on the **server**. UI hiding is convenience, never security.
5. Keep approvals, tasks, workflow runs, business records, notifications and comments separate in authority, even when shown together.
6. Prefer **modular monolith + durable background workers** at inception unless scale, constraints or existing architecture justify separate services. The five logical layers are not mandatory independently deployed services.
7. Every UI control must work, explain why disabled, or clearly indicate mock-only behavior. Label synthetic/sample data and local-only persistence. No pretend authentication, uploads, sends or agent execution.
8. Never expose secrets, raw connector credentials, protected logs or other tenants' data to UI, telemetry, exports or agents. Require consent and authorization for consequential external actions.
9. Use primitive → semantic → component tokens. Adopt Soft Enterprise defaults for new unbranded projects; preserve existing verified brands. Do not claim OpenAI/Apple/ClickUp internal tokens or distribute system fonts.
10. Validate code, visual layout, keyboard/assistive access, reduced motion, zoom, responsive cases, authorized deep links, failure/retry behavior and cross-domain reuse. Report exactly what was tested.
11. No destructive commands, migrations, live sends, deployments or production mutations without user authorization.

## Procedure
1. **Discovery & architecture**: Inspect and inventory routes/modules. Choose execution mode, decide whether existing stack is retained, identify the boundary between sample state and services. Read `references/architecture-contracts.md` and `references/security-governance.md`.
2. **Design system & shell**: Read `references/design-system.md` and `references/navigation-urls.md`. Implement IconRail + resizable ContextSidebar + primary WorkspaceCanvas + optional Inspector. Plan phone/tablet adaptations, keyboard focus and URL state first.
3. **Resource model**: Read `references/metadata-and-configuration.md`. Define typed, versioned app/module/resource/fields/masters/relationships, permission references, state machine, configuration publication and dependency validation.
4. **Functional surfaces**: Read `references/components-and-experiences.md`. Build only requested functions, using shared contracts for view bar, grid, filters, forms, inspector, quick comment, dashboard and page composition.
5. **Work and automation**: If relevant, read `references/workflows-and-agents.md` and `references/enterprise-services.md`. Keep business events and durable orchestration distinct from browser-side callbacks; require safe retries and agent supervision.
6. **Integration & data operations**: If requested, read `references/integrations-and-data.md`. No standalone API Management console. Support governed connector lifecycle, mapping, import/export and migrations.
7. **Verify**: Read `references/quality-and-evaluation.md`; use its cross-domain fixtures and tests. Run available typecheck/lint/build/tests; capture desktop/mobile layouts when browser is available. Be truthful about test coverage.
8. **Deliver**: Summarize modules, routes, behavior, permissions, mock/live boundary, files changed, test results, risks and prerequisites.

## Five logical layers
- **Foundation:** tenant, identity, organization/workspace, authorization, metadata, audit, storage.
- **Execution & Integration:** EDA, durable workflows/jobs, connectors, supervised agent gateway.
- **Shared Business Services:** work, scheduling, documents, communication, search, notifications, reporting.
- **Configuration:** app/module/resource manifests, masters, forms/views/pages, policies and publication.
- **Experience:** IconRail, ContextSidebar, WorkspaceCanvas, view bar, grid, forms, inspector, assistance.

## Source-of-truth ownership
- Metadata Registry owns fields/masters/relationships; Resource Runtime owns business record state; Authorization Service owns effective access; View Registry owns saved view definitions; Settings Resolver owns effective personal/workspace/organization preferences.
- Workflow Runtime owns approval decisions and execution state; Work Service owns tasks; Communication Service owns comments/messages; Notification Service owns delivery/inbox state; Scheduling Service owns reservations; Document Service owns files and versions; Audit Ledger owns audit evidence.
- Read models may aggregate these domains but must not silently become writable copies of their authority.

## Project design rules (owner decisions — override the UAB defaults and the master specification)
1. **Page header:** no breadcrumb row. The page title is shown in the **top bar** (left), not in the page body. The page description is never visible text; it sits in an ⓘ info icon right after the title that opens a dark tooltip (white 13px text, arrow pointing up, max ~340px) on hover, focus and tap, dismissed with Esc.
2. **Top bar layout:** left = (menu button on small screens) + page title + ⓘ; **centre = global search** (Ctrl/⌘+K); right = workspace switcher (compact, icon-only on phones), notifications, account.
3. **Two-line view toolbar on list pages:** **line 1** = `[view tabs][+] ……… [Export][Primary add]` with **one thin full-width line under it** (the active tab's accent underline sits on that line and **slides smoothly** to the newly selected tab, ~220ms ease; hover colours fade in; no motion when the user prefers reduced motion); **line 2** = `[search][Filters ⌄][Columns ⌄]` on the left; with the **record count (non-table views) and, when rows are selected, the bulk actions on the RIGHT end of line 2**; then directly the table. **No "All of: …" filter-chip line** (kept commented out in code) — active filters show as the accent dot on "Filters" and inside the Filters panel. Views start at the left; the **"+" add-view button** (icon only, borderless, tooltip "Add view") sits **right after the last view**. As views are added it moves right until the tab strip is full and **stops there**; further views **slide under it** (horizontal scroll, hidden scrollbar) and **fade out softly into the background** on the hidden edge (light gradient fade, not a dark shadow); the active view scrolls into view. Toolbar controls ("+ Add view", view tabs, search, Filter, Columns, Export, primary button) all use the shared compact height from rule 7. **View tabs are underline tabs** (like ClickUp/Notion): view-type icon + name, no box or border, muted text; the selected view = normal text colour, semibold, with a **2px accent underline**; the ⋮ menu appears on hover, keyboard focus and on the active tab. **Every view looks the same** — built-in or user-created, no scope/lock icons on the tab (scope shows in the tooltip and sidebar). The search input is ~220px wide. **The Filter button never shows a count**; it only switches to its active (accent) style when filters apply. Unsaved view changes use a compact "Unsaved ▾" menu (Save / Save as new / Reset). Filter chips go in a slim row below (hidden when empty).
4. **Data table look:** compact rows; small muted header labels in **regular weight (400)** with faint sort arrows always visible; no column separator lines (resize handle appears on header hover); statuses as a **coloured dot + coloured text** (no pill background); relation values as plain text (accent + underline on hover); visible "Actions" header on the sticky right action column, which shows a **soft shadow on its left edge only while more columns are scrolled under it** (table wider than its panel and not scrolled to the end); otherwise no line at all (borderless table, rule 17).
5. **Frozen pagination footer:** the table fills the page height; rows scroll inside it while a footer stays fixed at the bottom: **left** = "1–25 of N items"; **right** = numbered pages with ellipsis (‹ 1 2 … N ›) then a **custom "25 / page" dropdown** (options 25/50/100 "/ page", selected option tinted with a ✓, opens upward). No "Rows per page" text label (it is the accessible name). The record count lives in this footer, not above the table.
6. **Compact page spacing:** small outer padding around page content (≈8–12px top/bottom, 16px left/right); no large empty margins around the toolbar or table.
7. **One shared button size (common component, not per page):** the compact control token is **32px** for every button, icon button, compact input/select and view tab across ALL pages (toolbars, calendar, dialogs, footers, admin). Set it once in the token layer (e.g. `--c-control-h-compact: 32px`) and never override heights per screen; touch/coarse pointers still grow to 44px. Owner override of the locked 36px compact height. Full-size form inputs stay at 40px.
8. **Global type scale — exactly three text sizes, defined once as tokens:** **Primary 18px** (`--fs-primary`: page title in the top bar, record title in the inspector) · **Secondary 16px** (`--fs-secondary`: section/panel/dialog/chart titles, module title in the sidebar, key dashboard numbers) · **Supportive 13px** (`--fs-supportive`: everything else — table cells and headers, buttons, inputs, selects, view tabs, sidebar nav and section labels, filter chips, badges, form labels, help text, tooltips, footer, timestamps). No other font sizes anywhere: components reference these three tokens only, never raw px. Exception: on phones (≤760px) typed fields (inputs, selects, textareas) use 16px to prevent iOS auto-zoom.
9. **Custom dropdowns EVERYWHERE — never a native `<select>`:** every dropdown in the project (forms, filters, toolbars, footers, admin pages, dialogs, inline cell editing) uses the one shared `SelectMenu` component: trigger button + listbox popover; ↑/↓/Enter/Esc + type-to-jump; a search box when the list has more than ~8 options; flips up near the bottom; selected option = accent tint + ✓; placeholder, disabled, invalid and "None" (for optional fields) states. Height: 40px inside forms (matches text fields), compact 32px in toolbars, tables, footers and panels. Its popover layer sits above dialogs so dropdowns inside dialogs are never hidden. Inline cell editing commits immediately when an option is picked.
10. **Sidebar open/close toggle lives at the TOP:** a panel icon (◫) at the right of the context-sidebar header collapses it; when collapsed, the same panel icon appears at the top-left of the top bar to expand it. No collapse control at the bottom of the sidebar.
11. **Toolbar sizing:** on the tabs line the Export and primary buttons always keep their full width; the view tabs take only the remaining space (flex-basis 0) and scroll/fade — tools must never be clipped off-screen. Keep the active view visible by scrolling only the tab strip (never `scrollIntoView`, which can shift the page).
12. **One global tooltip component (never CSS pseudo-element tooltips):** a single tooltip layer mounted once at the app root renders every tooltip in a portal above all content, so it is never clipped by tables, sticky columns or scroll areas. Dark bubble (supportive text, ~7px radius) with an arrow; opens above and flips below / clamps to the viewport; icon-rail tooltips open to the right. Trigger with a `data-tooltip` attribute (no native `title` tooltips on page elements); opens on hover (~350ms) and keyboard focus, closes on leave, scroll, click and Esc.
13. **Truncated text always reveals itself:** any text cut off with an ellipsis or line clamp shows its full text in the global tooltip on hover/focus — automatically, without per-cell code. Full text takes priority over other hints on the same element.
14. **Date format:** every date column/cell shows the **date only as "16 Oct, 2026"** (day, short month, comma, year) — also for date-time values. The full value appears on hover/focus in the global tooltip as **"Fri, 16 Oct 2026 08:30 AM"** (weekday, date, 2-digit 12-hour time + AM/PM when a time exists). Render dates through the shared `DateText` component; never use raw `toLocaleString()`.
15. **Empty values:** never show "—" or blank for missing data. Use the shared `EmptyValue` component: italic **"N/A"** in a **very light grey** (`--c-empty-value-fg` ≈ 22% text over white — lighter than disabled text), **no icon**, accessible name "Not available". Applies to table cells, details, review screens and admin tables.
16. **Table checkboxes:** header and row selection checkboxes are centred in the same column so they form one straight vertical line. **Row checkboxes are hidden until the row is hovered** (fade in); they stay visible when checked, while any row is selected, on keyboard focus and always on touch screens. The header checkbox is always visible.
17. **Table header & columns — borderless table:** the table has **no outer border/frame, no vertical lines between body cells** — only light horizontal row lines; **the header keeps short vertical dividers between its cells (none after the last data column, i.e. before Actions)**; the **sticky Actions column keeps a 1px divider on its left, plus the soft shadow while more columns scroll under it**; the column-resize handle line appears only while hovering a header; the **sort arrow sits to the RIGHT of the label** in every column; the **sorted column is shown only by its label and arrow turning dark** (text colour) — no tinted column. The **Actions column is pinned at the far right, its title and icons centred, and its width fits exactly the number of row icons** (n × 30px icons + 2px gaps + 16px padding, e.g. 3 icons = 110px); column widths are **minimums** — when the table is narrower than its panel, the **spare width is shared proportionally across the data columns** (the last data column absorbs rounding) so there is no empty gap; Actions and the checkbox column never grow. When columns exceed the panel, the table scrolls horizontally instead. **Every table column is LEFT-aligned — text, numbers, money and dates alike** — and each value starts exactly under its header label. Hover-only controls inside cells (e.g. the inline-edit ✎) float over the right side of the cell and never reserve space; the ✎ is a **plain icon with no background box** (a light fill appears only while the pointer is on the ✎ itself). **Clean table style:** the header row is **white like the rows** (`--c-grid-header-bg` = `--s-panel`) with small muted labels and **one bottom line**; **list pages are fully WHITE** (no grey canvas behind the toolbar, chips or table) and the **table runs edge to edge** across the page width — no card, no radius, just one line above the header; rows are white with light row lines and a **very soft hover tint** (`--c-grid-row-hover-bg` ≈ 3% text over panel).
18. **Toolbar panels & button states:** "+ Add view" (and Rename/Duplicate/Save as new view) open as an **anchored panel under their trigger — exactly like the Columns panel — never a centred modal**. Only the toolbar button whose panel is currently open looks pressed (neutral hover-grey fill); no button stays "selected" otherwise. Active filters are shown by a small accent **dot** on the "Filters" button plus the filter-chip row, not by a permanently highlighted button. **Segmented controls (e.g. Compact | Comfortable, Table | Board | Calendar) hug their content** — the grey track is only as wide as its options.
19. **Never show the same information twice:** if text is available in a tooltip, do not also print it visibly next to the element (e.g. disabled menu items show only their label; the "why it is disabled" reason appears in the tooltip, plus a screen-reader-only copy).
20. **Expandable rows (master–detail):** the expanded content is **NOT a card** — it sits directly on the white table surface, indented under the expand chevron: **no title line** (the table caption is screen-reader only) — just a **plain numbered table** (`#` column first) with muted regular-weight headers, a line under the header, light row lines and a total row when there are several items; every header aligns exactly with its values (the inner table never inherits the main grid's sticky header/cell sizing). The open row's chevron turns accent. The expanded block ends just before the Actions column and **stays fixed in place when the table scrolls horizontally**. **The last table row keeps its bottom border line.**
21. **Multi-value cells (chips/tags):** show the values as chips on **one line, only as many as fit the column width, then a "+N" chip** (accent tint). Hovering or focusing "+N" opens a **list tooltip**: an uppercase heading with the count and field name (e.g. "5 WORKING DAYS") followed by every value on its own line. Rows never grow taller because of chips; the chip count recalculates when the column is resized. Use the shared `OverflowChips` component.
22. **Bulk actions live on the search line (line 2), not in a separate bar:** when rows are selected, "N selected · Change status ▾ · Export selected" appear at the **right end of line 2**, preceded by a short vertical divider. No "Clear" button (deselect with the header checkbox).
23. **Explanatory text goes into an ⓘ info icon, never as visible sentences:** descriptions and help text (page/dialog/panel descriptions, form-field help, side notes such as "Saves the current filters…", "Shared views share the definition only…") are shown only through the shared `InfoTip` (ⓘ) placed right after the related title or label, with a screen-reader-only copy for `aria-describedby`. The ⓘ never draws its own bubble — it uses the one global tooltip layer (rule 12), so its tooltip is never clipped inside panels, popovers, dialogs or tables; it opens on hover, keyboard focus and tap/click. Disabled-option reasons go in the tooltip. Keep as visible text only things the user must see without hovering: data, statuses, warnings/errors, confirmation consequences and empty-state messages.
24. **Custom date picker everywhere — never a native date/datetime input:** every date or date-time entry (forms, filters, calendar "go to date", studio defaults) uses the shared `DatePicker`: trigger styled like the dropdown with a calendar icon and the project date format ("16 Oct, 2026" / "16 Oct, 2026 09:00 AM"); popover calendar with ‹ month › navigation, **Sunday-first** 6-week grid (Su Mo Tu We Th Fr Sa), **round** day cells, today ringed (circle outline) in accent, selected day filled accent, other-month days muted; keyboard ←/→/↑/↓, PageUp/PageDown, Home/End, Enter, Esc; footer "Today", "Clear" (optional fields) and, for date-time, a time row (hour · minute in 5-minute steps · AM/PM using the custom dropdown) plus "Done". 40px in forms, 32px in toolbars/filters.
25. **Filter panel = simple form, Apply to commit:** the toolbar button reads **"Filters ⌄"** (sliders icon, chevron flips when open; **every toolbar button that opens a panel — Filters, Columns — shows this ⌄/⌃ chevron**) and opens an anchored panel (~320px) laid out as a form: label above each control; **Status first** — a full-width segmented control "All · value · value" when it has ≤ 3 values, otherwise a multi-select dropdown; then up to 6 choice fields — master / relation as multi-select dropdowns, yes-no as a single dropdown — defaulting to **"All"**; a divider; then up to 2 date fields as a **date range picker** ("Select date range") — **two months side by side** (one on phones), bold short titles ("Oct 2026"), « ‹ (previous year / month) on the left month and › » (next month / year) on the right month, Sunday-first weekdays, round days, today ringed, other-month days light grey, range = continuous accent-subtle band with filled circles at start/end; first click = start, second = end, hover previews. Footer: two equal-width buttons **Clear** (removes all filters) and **Apply** (primary) — nothing changes until Apply. The full AND/OR condition builder (locked requirement) stays available via an "Advanced conditions" link in the panel — compact (~480px, rows = field · operator · value · ×), right-aligned to the button and always kept fully on screen; views whose filters need OR/nested groups open directly in the advanced editor. Filter chips read naturally for dates ("Start from 1 Oct, 2026", "Start until 28 Oct, 2026").
26. **Multi-select dropdown with checkboxes:** whenever a field can hold or filter by several values, use the shared `MultiSelectMenu` — same trigger as the single dropdown; the popover starts with a **search box (🔍 icon, borderless, divider below — always shown)**, then a bold **"Select all" row with its own checkbox** (checked = all, dash = some, empty = none; acts on the currently searched options; label switches to **"Deselect all"** when everything is checked) and a divider, then a **checkbox per option** (accent-filled when checked), and — when anything is selected — a **footer "N selected" (left) · "Clear all" (right, accent)**. It **stays open while toggling** and clicking options keeps the cursor in the search box. The trigger shows the **selected values as accent chips** on one line (as many as fit, then "+N" with a list tooltip); nothing selected → placeholder (filters: "All"). Use it for multi-value form fields (e.g. working days, access needs) and for every choice filter in the filter panel (status with more than 3 values, master and relation fields), which produce an "is any of" condition; booleans stay single-select and status with ≤ 3 values stays a segmented control. An existing "A is x OR A is y" filter on one field opens in the simple panel as a multi-selection.
27. **Clean, aligned forms:** form section titles ("Who", "When & where", "Details", "Restricted"…) are **not shown** (kept only as screen-reader legends; sections continue the same grid with no divider). Number inputs have **no up/down spinner arrows**. Every field in a row lines up: same label-row height (with or without ⓘ), same control width — prefixes/suffixes like "$" and "min" sit **inside** the input box, never beside it.
28. **Side drawers (any project):** every side drawer — create/edit forms, help, **and the record view / details panel** — opens the SAME way: over the page from the right with a dimmed backdrop (never a panel docked beside the table that squeezes it), same width (560px), and has a header the **same height as the app top bar** with the title in the **primary text size (18px)** — the ⓘ beside it when there is a description. **No popup ever has a × close icon** — not side drawers, not centred dialogs (forms, quick create, search, payments, confirmations). Every popup closes with a **Cancel button in the footer** (confirmations may word it "Keep editing" / "Keep as is"); popups without their own actions get a default footer **Cancel**; multi-step wizards always show Cancel (plus Back after step 1). Esc and clicking the scrim still close. In a record-view drawer the header holds the record title + status chip, with prev/next, expand, open-full-page and pin icons on the right; workflow actions that would read "Cancel" are named in full ("Cancel appointment") so they never clash with the footer Cancel. **If the drawer has an Edit action, the Edit button sits in the footer next to Cancel** (Cancel · Edit, Edit primary) — not among the buttons at the top; workflow actions (Check in, Reopen…) stay at the top. Clicking Edit turns the same drawer into the form and the footer becomes Cancel · Save changes, pinned at the bottom (the comment box hides while editing).
29. **Form fields per row follow the container width (any popup, dialog, drawer or page form):** never one long single column in a wide popup. Fields flow **1 → 2 → 3 per row** automatically from the available width (each column ≥ 220px, max 3): a ~520px quick-create dialog or a 560px drawer shows 2 per row, wider containers 3, phones 1. Long text, line items and multi-selects take the full row. Section metadata `columns` is only a hint — width decides.
30. **Always confirm before deleting (any project):** every action that deletes, removes or discards data — records, saved views, drafts, configuration items, attachments, rows — first opens an **alert box** (`role=alertdialog`): title "Delete <thing>?", one sentence saying what is lost and what is not, footer **Cancel** (focused) + red **Delete** (or "Remove" / "Discard draft"). Nothing is deleted until it is confirmed. Use the one shared helper (`confirmDelete({ title, message, confirmLabel, onConfirm })` + a single `ConfirmHost` mounted in the app), never `window.confirm` and never a one-click delete.
31. **Calendar / time-grid blocks never cut text:** the block's height decides what it shows — tall: name · time range · status; medium (≈30 min): name · time range on 2 lines; tiny (≈15 min): ONE line, name (gets the …) then start time (never cut); the full details are in the hover tooltip. Time ranges are compact ("08:30–09:30 AM" when both share AM/PM). **Overlapping bookings sit side by side** in equal columns instead of covering each other. The hour-label column is wide enough for "10:00 AM" (≈76px); lane headers with a note (e.g. "maintenance") put the note under the name. Booking blocks are a soft tinted card **without a coloured left line**; overlapping bookings get a dashed outline. Usage hints ("Click an empty slot to book…") go in an ⓘ next to the date, not as text under the grid. The calendar shown as a **view inside a list page looks exactly like the standalone calendar page** (same panel, toolbar, lanes and blocks; its count sits on the search line). The calendar panel **fills the screen down to the page bottom** (no empty area below it, no page scroll); only the time grid scrolls inside it, with the lane headers sticky.
32. **No accent indicator lines in front of items:** selection/active state is shown by the item's own tint, never by a coloured bar before it — no bar left of the active icon-rail icon, no coloured left border on calendar bookings or cards, no accent line at the start of the active table row.
33. **Context sidebar style:** the sidebar has a **light grey surface** (`--c-sidebar-bg` ≈ 2.5% text over white; hover ≈ 6%) has **tight option spacing** (30px rows, 1px gap — owner override of the 34px default; separators 12px above / 4px below) and is split by **plain section separators** — muted, regular-weight, sentence-case supportive text such as "Pages", "Menu", "Pinned", "Recent" (no uppercase, no lines). It supports **rows with an icon** (icon + text, e.g. pages, pinned, recent) and **rows without an icon**: a collapsible group row shows chevron ⌄/› + label + a muted **count** on the right, and its children are **text-only rows indented under the group label**. Active row = light accent fill + accent text (its count turns accent too). **Child rows can be text-only (default) or carry icons** — a module opts a group into child icons (`navChildIcons: ['invoices']`); both indent under the group label. **Search at the top:** a "Find a page (N)" box (N = all options of the module) filters every option into one flat "Results" list (with icons), Esc clears. **Favourites:** every option shows a ☆ on its right on hover/focus (always on touch); clicking it fills the star (accent) and the option **moves up into a "Favorites" section at the top** of the sidebar (shown in every module, saved per user); clicking the filled star removes it. Text-only options use their view-type icon inside Favorites/Results. **Layering:** the sidebar and its resize handle always sit above the page content (sticky table cells must never cover the handle), and the page content isolates its own sticky layers.
34. **Profiles & people in tables — mandatory in EVERY project:** whenever a resource has people or profile data (assignee, owner, members, team, auditors, employees, customers with photos, products with images…), the build **must** (a) add a dedicated rich view option for it (e.g. "Team view") as described below, and (b) render any field holding **several people** as the avatar stack + people card in every table where it appears; single-person and image fields use the avatar/picture presentation inside that rich view. **Rich rows live in their OWN view option — normal tables stay one-line:** ordinary list views keep plain one-line rows (no avatars, photos, initials tiles or extra lines). Rich presentation is offered as a **separate saved view** (e.g. Tasks → "Team view") with `rowLines: 3`, where **one row mixes 3-line, 2-line and 1-line cells**: a field's `subFields` become muted lines 2–3 under its value (e.g. Title / Due date / Priority), a people relation with `display: 'person'` shows a **32px avatar + name + muted subtitle** (`personSubtitle`, e.g. role), and plain fields stay one line; empty sub values are skipped (never "N/A") and sub fields are not repeated as columns. **Several people** (`people` field) show as **overlapping 26px avatars** (max 3, then an accent "+N"); hovering or focusing opens a **compact people card** (≈248px wide): an uppercase header band ("6 PEOPLE ASSIGNED") on a light-grey strip, then one row per person — 32px avatar, name (medium) and a muted subtitle (ellipsis), arrow pointing at the stack; it shows **at most 5 people and scrolls inside** for more (scrolling inside never closes it; scrolling the page does). Avatars use the person's photo when there is one, otherwise a soft coloured initials circle. Forms: `people` = multi-select dropdown; `image` = local Upload / Replace / Remove with a preview tile. **A rich view shows a visible "2 lines | 3 lines" switch on the tools line** (after Columns, 32px segmented control): 2 lines = value + first sub line (text only), 3 lines = value + two sub lines **plus an image section** — a 40px rounded picture at the start of the main cell (`leadingImage` + `leadingImageMinLines: 3`; initials tile when a record has no picture); switching marks the view "Unsaved" like any other view change. **Seed-data changes:** when sample data gains new fields, bump the local data version ONCE after all seed edits are in (a version bumped before the data is complete leaves browsers with half-upgraded data, e.g. empty people columns).

## Priority and limits
Explicit user requirements > existing code/brand/constraints > UAB V2 defaults. Security, accessibility, and truthful reporting remain mandatory. The goal is *working software*, not a collection of attractive screens. Do not add unnecessary modules or a backend for a frontend-only request.

## Repeatable evaluation gate
For a packaged skill QA run, execute `python scripts/evaluate_skill.py` from the skill directory. It tests package links, mandatory instruction coverage and three synthetic CRM/HRMS/Inventory manifest fixtures. Inspect `evals/results.json` and report failures. **These static checks do not demonstrate generated frontend behavior, real authorization, browser accessibility, service integrations or production readiness.** To validate actual skill performance, run the six prompts in `references/quality-and-evaluation.md` in isolated projects, inspect generated code and execute each project's test/build/browser checks; don't conflate prompt instructions with outcomes. Do not overwrite the installed skill until actual-app gates pass or the user knowingly accepts these limitations.
